# Track families: the complete catalog of flat (1-wide) seamless mechanisms per box

Brief (vjeux via the coordinator, 2026-10-18 21:09Z): "Can we search exhaustively all the 'families'
and see if we can wire them?" A family = a door mechanism: the pistons that move the 9 door blocks
and the paths the blocks take (wiring and timing aside). Records at the start: flat-b-v7-full 80b
(8x10x1, center exits DOWN via an elevator below) and flat43-full / fl81m 81b (9x9x1, center exits
UP via an elevator above).

Outputs (all generated by `mctas door families`, never edited by hand):
* [CATALOG.md](CATALOG.md) + [CATALOG.tsv](CATALOG.tsv): per box (volume order) every minimal 2D
  mechanism that fits, with pistons, schedules, symmetric train, the wiring checks (`wire` class and
  track box56's `door topology` verdict: strict / permissive / memory / no), the simulator replay
  with ideal inputs, and machine-readable files `mech/<id>.txt` (door + pistons, no wiring) +
  `mech/<id>-{sym,oc}.ideal` (`door ideal` schedules; power windows: `door ideal --sweep`).
* [ROWS.md](ROWS.md) + [ROWS.tsv](ROWS.tsv): strip doors (boxes of height 3-5 / width 3-5): every
  row mechanism, exhaustive.
* `unresolved/WxH.txt`: the candidates of a box the solver could not decide (re-check with
  `door families --resolve unresolved/WxH.txt --boxes WxH --cap N`).

## Model
* A fast grid port of mech-synth's macro piston model (`PistonStructureResolver`, push limit 12,
  sticky pull of the block two ahead, retracted pistons movable, extended pistons / heads / obsidian
  immovable), in the door plane: pistons face E/W/U/D. `P` = 2 gt pulse (push and spit, or extend
  into a gap and pull the block beyond), `L` = level toggle. A level-on that cannot extend is
  refused; a move that would leave the box is refused (the box holds every state).
* Open test = FULL seamless for a flat door (`door properties`): the 3x3 empty; the 12 ring cells
  hold only air, door blocks or plain blocks (no piston body or head, no obsidian); every ring cell
  that some state of the cycle fills but the open state leaves empty has air or a door block right
  behind it (the hole rule). Closed: the door plane's ring is hidden behind the door blocks, so a
  flat door is QUART on both sides by construction; `rest-ring` says whether the rest state also
  keeps pistons out of the ring (the coordinator's stricter reading).
* Solve = the WHOLE state graph of the pulse model (pulses on every piston, levels only on pistons
  extended at rest), capped at 300k states; then goal-directed A* (pulse model, 300k) on the capped
  ones; what neither decides is UNRESOLVED (counted per box). `--resolve` re-checks unresolved
  candidates by exhaustive reachability of an open state with a compact visited set (20M states).
* QUASI-CONNECTIVITY (v3, 23:10Z; v1/v2 ignored it): whatever powers a piston X also gives X's
  cell a neighbor signal, so a retracted, unpowered piston Y right below X is armed and fires with
  X's update: Y follows X's pulse (evaluated while X is out, so a Y facing up into X is blocked:
  the elevator's lift under its pulled piston), X's level-on arms Y (held), X's level-off releases
  it; a piston held powered at rest above a retracted one is rejected (unstable). Published
  sequences spell the coupling out (the coupled piston's own event follows the event that fires
  it; it needs no wiring of its own); ideal plans spell it out per edge. Why: v2's 8x8-119 family
  (elevator pulled back right above BL's puller) failed its ideal replay because the elevator's
  power QC-fired BL's puller; with the coupling the solver times BL's exit to that pulse and the
  oc plan replays (4 positions x 2 cycles).
* Symmetric train: pistons used once per edge and touching no cell another piston changes are
  "edge" toggles (fired as a block at the start or the end, every split tried); the core gets a
  product BFS of the run from rest and the run from open under the same events.

## Generator (the bounds of the 2D catalog)
* Box W x H, the door at every offset (left-right mirror offsets skipped: mirror images merged;
  up/down is not a symmetry: quasi-connectivity and gravity).
* The CORE: the center leaves straight in exactly 2 moves; the edge block on its line leaves in 2
  moves (any path not ending on the center's park cell).
* The 7 other perimeter blocks: 1 move out by a pull-type sticky puller (retracted, 2 cells away),
  or (`--two N`) up to N of them by any 2-move path.
* Every move gets every provider: a PULL by a sticky piston 2 cells ahead (retracted or extended at
  rest), a PUSH by a piston 1-2 cells behind (sticky or normal), or a piston already placed reused
  from its rest cell or LIFTED one cell along its own axis by one sticky lift piston (the elevator).
* At most P pistons (`--pistons`; the published catalog: 11), no helpers, no slime/honey.
* Working candidates are reduced to MINIMAL mechanisms (greedy: no piston can be dropped).
* The solver may find solutions outside the plan that generated a candidate (riders dragged
  sideways to serve two lines, long block shuffles): real macro-model solutions, kept, but their
  schedules are long (open ~20 / close ~46 events): practically unwirable.

## Strip doors (`--rows`)
In a box of height 3-5 nothing can pull a block out of the 3x3 vertically, so the blocks slide
sideways in their rows; each row is solved on its own: EVERY placement of <= k E/W pistons
(sticky/normal, retracted/extended) in the row's arms (<= 5-7 cells each), exact solve, minimal,
mirror-merged. Results (k = pistons per row):
* k <= 3: no row mechanism at any width <= 13.
* k <= 4: narrowest row 12 (arms 4+5): 12x3 / 12x4 / 12x5 with 12 pistons.
* k <= 5: width 11 (arms 4+4, 198 minimal row mechanisms): 11x3 / 11x4 / 11x5 (33 / 44 / 55) exist
  in the macro model with 15 pistons; nothing at width <= 10.
* k <= 6 (arms <= 7): still nothing at width <= 10.
* No row mechanism is STATIC: every one moves pistons along the row (walker pairs of sticky pistons
  facing each other, pullers dragged outward), so pistons fire from several cells, some inside the
  3x3 (wire3 / wire5 columns of ROWS.md).

## Wiring checks
* `wire` (families.rs): free cells minus the ring, the swept cells and the cells behind open holes
  split into regions; each (piston, firing cell) is fed from a region touching it or its QC cell;
  a region with pistons only it can feed but no lever needs a link (an observer on a changing
  mechanism cell next to it) with the right pulse parity. A one region / B links with parity /
  C needs a merger / X impossible.
* `topology` (track box56's `door topology`, topology.rs): strict / permissive (chain merges) /
  memory (added here: a waxed copper bulb T flip-flop + comparator in a region with >= 2 free cells
  turns an even link into one window). On the v1 catalog (6b2d389, P <= 10): 2 strict (8x8-102,
  8x9-111), 15 permissive (all rider shuffles), 26 memory (7x8-028/029 with a 13-pulse train).

## What did not work / caveats
* The first generator (every block every 1-2 move path, every provider, DFS over 9 blocks) never
  finished even 7x7: the core + others split made it tractable.
* Full-graph BFS blows up on independent toggles (each pull-type side piston doubles the space):
  ~40 % of candidates hit 300k states. A* resolves the working ones fast; proving the rest
  impossible needs a smarter method (partial-order reduction / decomposition): the main gap in the
  "exhaustive" claim.
* The macro model ignored quasi-connectivity until v3: v2's 8x8-118..129 plans failed in the
  simulator (an elevator piston pulled back above BL's puller QC-fires it).
* door topology's parity rule is a heuristic (wire56: observer timing gives odd counts from
  double firings); rider shuffles get "strict" from topology but fire pistons inside the 3x3.
* mech-synth's ideal_plan finds no input cell for 68 entries (pistons boxed in by the mechanism).
